# LOL-GM AI 작업용 룰북 안내서 — 비규범 문서

**목적:** ChatGPT·Codex가 오래된 규칙을 재제안하거나 서로 다른 게임 엔진/문서를 섞지 않도록 하는 **읽기·검증·개정 절차**다. 이 안내서는 **게임의 규칙이 아니다.** 규칙의 유일한 본문은 [docs/rulebook/](rulebook/README.md)에 둔다. 사용자 승인 없이 이 문서의 절차를 명분 삼아 새로운 규칙을 만들 수 없다.

## 1. 먼저 읽을 것 — 작업 주제별 길찾기

| 작업 키워드 | 가장 먼저 읽을 확정 규정 | 인접 제약 (실제 작업 전 읽기) | 승인 근거의 대표 이슈 |
|---|---|---|---|
| 세계 날짜, 일정, FA | [CAL](rulebook/20-CALENDAR.md) | [TRANS](rulebook/30-TRANSFERS.md), [COMP](rulebook/10-COMPETITIONS.md), [CORE](rulebook/00-CORE.md) | #234, #311, #321 |
| 대회 포맷, 국제전, 1~N부 | [COMP](rulebook/10-COMPETITIONS.md) | CAL, [GOV](rulebook/70-GOVERNANCE.md), CORE | #311, #323, #324 |
| 이적, 라이선스, 바이아웃 | [TRANS](rulebook/30-TRANSFERS.md) | CAL, [BIZ](rulebook/60-BUSINESS.md), COMP | #224, #321, #322 |
| 세계 랭크, 성장, 스카우팅 | [PLAYER](rulebook/40-PLAYERS.md) | [MATCH](rulebook/50-MATCH.md), CORE, CAL | #251 댓글, #232, #236, #238 |
| 실제 경기, 스크림, 밴픽, 패치 | MATCH | PLAYER, COMP, CAL, CORE | #233, #232, #235 |
| 구단, 참가 계약, 후원, 수익 | BIZ | TRANS, COMP, GOV, CORE | #237, #251, #316, #317 |

| 저장·역사·원장·장기 결정론 | CORE | 실제 변경 도메인의 규정, 당시 시즌/계약 기록 | #241, #239 |
| 감독 UI·뉴스·저장 슬롯 | [UI](rulebook/80-EXPERIENCE.md) | CORE, TRANS, PLAYER | #225, #273, #280 |

**빠른 찾기:** 분야별 조항 ID는 `CORE-001`, `COMP-001`, `CAL-001`, `TRANS-001`, `PLAYER-001`, `MATCH-001`, `BIZ-001`, `GOV-001`처럼 **파일 접두어와 고정 식별자**로 표기된다. 정확한 번호를 검색하고 해당 조항의 **원본 근거 링크까지** 확인한다. AI는 자신이 읽지 않은 규칙을 '없다'고 단언하지 않는다.

## 2. 판단 순서 — 작업마다 동일

1. **요청의 규칙 ID/주체/시계/시즌 파악:** 누가 무엇을 바꾸는가? 게임 내부 사무국 개편인가, 코드 버그 수정인가, 사용자의 상위 규정 변경 요청인가?
2. **먼저 규정집 + 인접 도메인 확인:** 단일 장의 문구만 읽고 같은 선수·시계·대회·원장 조건을 누락하지 않는다.
3. **새롭거나 충돌 가능성이 있으면 실제 사용자 승인 원본 재검증:** 각 조항의 GitHub 이슈/댓글, 해당 시점 이후의 **더 최신 명시적 선택**까지 읽는다. 예컨대 #311 구형 7일 vs 2026-10-29 별도 기간 폐지, #232의 랭크 미결정 vs 2026-10-18 #251 확정처럼 이슈 상단을 기계적으로 신뢰하지 않는다.
4. **규정/제안/코드 상태 분리:** `확정 규정` / `초기 설정에만 적용` / `과거 규정으로 대체` / `미결정` / `코드 구현됨` / `CI 통과` / `main 반영`은 별개의 사실이다. **Draft PR과 과거 CI PASS는 실제 게임의 현재 규정이라는 증거가 아니다.**
5. **동일 작업 원본의 기존 PR·이슈 대조:** 코드가 대상이라면 현재 `main` 및 **활성 PR의 정확 HEAD·변경 파일·작성자/소비자**를 대조한다. #242 순서, #241 통합 게이트, 단일 사건/재정/경기 writer를 유지한다. 오래된 브랜치·이슈의 예시를 근거 없이 다시 활성화하지 않는다.
6. **결과 범위를 정확히 보고:** `문서 편찬` / `문서 PR 등록` / `코드 수정` / `테스트 성공` / `main 병합` / `실행된 세계에서 검증`을 구별한다. 현재 수행하지 않은 것을 완료로 표시하지 않는다.

## 3. 규칙을 추가하거나 고칠 때

- **미확정 아이디어를 규칙집에 넣지 않는다.** 날짜 예시, 수치형 매칭 임계값, 이사회 의석수, 임시 QA 기준, PR 설명을 확정값처럼 작성하지 않는다.
- 기존 규칙을 수정한다면 **고정 ID 유지 + 해당 규칙의 한 파일만 수정 + [규정집 변경 기록](rulebook/CHANGELOG.md) 갱신**. 원래 승인 출처는 보존한다.
- **게임 내부에서 합법적으로 바뀐 시즌별 규정은 게임 세이브/대회 규정 스냅샷으로만 관리**한다. 게임 내 AI가 지역 PO를 8팀으로 개편할 때마다 GitHub 상위 룰북을 고치지 않는다.
- 룰북과 더 최신 승인 원본이 충돌하면 **사용자의 나중 명시적 결정이 우선**이고 룰북의 해당 조항을 교정할 근거가 된다. 어떤 해석이 맞는지 아직 확인되지 않으면 **추측으로 정본을 덮지 않는다**.
- 분야별 규칙을 복사해 이 안내서에 다시 정의하지 않는다. 이 표는 *파일로 이동하는 색인*일 뿐이다.

## 문체 점검 — 의미 변경 금지

규정 파일의 신규·기존 조항은 **문어체의 규정형 문장**으로 작성한다. ‘그해’, ‘원팀’, ‘가짜’, ‘딱지’, ‘꾸며내다’ 같은 비공식 표현은 상황에 따라 ‘해당 연도’, ‘원소속 팀’, ‘실재하지 않는/허위’, ‘고정 분류’, ‘허위로 생성하다’ 등 정확한 법률·운영·개발 문맥의 용어로 교정한다. 다만 **문구 교체 시 의무 수준과 예외의 적용 범위가 달라지지 않도록 원문 근거를 확인한다**. 원본 승인 발언·코드 식별자·사용자에게 표시되는 실제 고유명은 문체만을 이유로 덮어쓰지 않는다. 이 절은 **비규범적 편집 가이드**이며 새로운 게임 규칙을 만들지 않는다.

## 4. 의도적으로 룰북 밖에 둔 것

`docs/POLICY_PRECEDENCE_2026_11_01.md` 같은 충돌 감사, `docs/DEVELOPMENT.md`의 개발 단계/예시, GitHub 미병합 PR의 구현 방법, 테스트 진단, 인사 투표 임계값·랭크 대기시간 수치 등의 미확정 제안. 작업 중에는 검토할 수 있지만 **승인된 상위 게임 규칙으로 승격하지 않는다**.

**참고:** 최초 발행은 상위 확정 규칙의 1차 편찬이며 개별 GitHub 이슈의 수백 개 승인 세부 항목을 모두 이관했다고 주장하지 않는다. 검토 범위에 없는 세부 정책은 기존 승인 기록을 반드시 확인한다.
