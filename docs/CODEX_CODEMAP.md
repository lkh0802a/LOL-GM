# Codex 변경 파일 중심 코드 맵 — 재개 시 최소 탐색 규칙

> **상태:** 현재 사용 가능한 Git/rg 절차 + **#242 최신 0-B에서 코덱스가 최우선으로 구현할 최소 자동 CLI의 수용 계약**. `scripts/codex-impact-map.mjs`는 **아직 없으므로 존재하는 명령처럼 실행하지 않는다**. 오직 기존 Codex가 구현하며 다른 AI·예약·작업자 분담은 추가하지 않는다. 지도는 근거 있는 **탐색 힌트**이지 완전한 의존성 그래프나 테스트 PASS 증명이 아니다.

## 1. 지금 즉시 사용: 변경 범위만 좁혀 보기

1. **현재 이슈·PR 체크포인트·정확 HEAD부터 확인.** 우선 `git status --short`, `git log -1 --oneline`과 담당 PR 파일 목록을 확인한다. 완료된 이슈를 다시 분석하지 않는다.
2. **변경된 추적 파일·신규 파일을 모두 파악.** 로컬에서 origin/main을 조회할 수 있는 경우 아래 예시를 사용한다. 다른 기준 브랜치나 PR base라면 실제 base를 쓴다.

```sh
git diff --name-only "$(git merge-base origin/main HEAD)" HEAD
git diff --name-only
git ls-files --others --exclude-standard
```

3. **모듈 구분은 기존 manifest의 실제 목록으로.** `scripts/artifact-modules.mjs`의 `ENGINE_MODULES`/`UI_MODULES`을 조회하고 `src/artifact/`의 조립 순서를 확인한다. 모듈 개수를 하드코딩하지 않는다.
4. **해당 함수·상태 키 중심 소비자·연관 테스트 후보를 검색.** 먼저 변경된 파일의 함수 정의, 호출/전역 상태 읽기·쓰기와 키워드를 찾고, 확인된 식별자만 관련 소스·테스트에서 검색한다.

```sh
rg -n '변경한함수명|실제상태키' src/artifact scripts --glob '*.js' --glob '*.mjs'
rg -l '변경한함수명|실제상태키' scripts --glob '*acceptance*.mjs' --glob '*runner*.mjs'
```

5. 후보 테스트는 `package.json`의 실제 명령, `scripts/*runner*.mjs`의 임포트, `scripts/test-harness.mjs`의 실제 fixture 로딩을 확인한다. 단순 파일명 일치만으로 커버리지를 주장하지 않는다. 확인된 테스트가 없다면 **미확인**으로 표시한다.
6. **바뀐 원본 writer → 소비 함수 → UI/세이브·당시 역사 → 집중·인접 테스트**만 읽고 작업한다. 공통 세계 시계/경기 결과/계약·재정/시드와 연동되면 인접 모듈을 반드시 추가 조회한다. 변경 파일 외 영향 없음이라고 단정하지 않는다.

## 2. 0-B 우선: 최소 자동 코드 맵 구현 계약 (Codex 단독)

**사용자 최신 결정:** [#242 0-A PR #264 운영 문서 검토/병합 판단](https://github.com/lkh0802a/LOL-GM/issues/242) 다음에, **동일 Codex가** 최소 CLI를 **별도의 작은 코드 PR 한 번**으로 실제 구현하고 테스트·최종 HEAD CI를 확인한다. 완료 후 바로 #246/PR #262 등 기존 개발 큐로 복귀. 정밀한 의존성 그래프·복잡한 인덱스/상시 캐시 시스템을 만들기 위해 이 단계를 끝없이 확장하지 않는다. 별도 모델·에이전트·역할 분담·예약 추가 금지.

### MVP 필수 범위 (구체적)

1. **변경 파일 자동 감지:** 실제 PR 기준 브랜치/merge-base와 HEAD, staged/unstaged/untracked 파일을 안전하게 구분하고 삭제·이름 변경도 놓치지 않는다. `origin/main` 부재·미커밋 상태에서는 실패 원인을 알리고 해당 인자를 요구하거나 명시적 안전 경로로 전환한다. Git 미사용/실패를 무조건 '변경 없음'으로 오해하지 않는다.
2. **모듈·기초 의존성:** `scripts/artifact-modules.mjs`의 현재 `ENGINE_MODULES`/`UI_MODULES` 목록을 그대로 사용한다. 변경 파일 안에서 확인한 식별자·상태 키를 근거로 `src/artifact/`의 직접 사용처와 소스 경계 후보를 좁게 찾고, **조립된 전역 JS**와 동적/간접 호출을 고려해 확정·후보·미확인 관계를 분리한다.
3. **테스트 후보 자동 추천:** `scripts/*-acceptance.mjs`, 실제 테스트 러너/하네스/명령을 검색하고 **테스트 파일 경로와 연결 근거**를 출력한다. 함수명/이름만 같은 불분명한 후보는 '추정'이라고 표시한다. 테스트 없음·범위 불명은 명시적으로 보고한다.
4. **가벼운 결과 재사용:** 같은 정확 HEAD + 작업트리/manifest/관련 러너 입력이 동일하면 이미 구한 탐색 결과를 불필요하게 재계산하지 않는다. 소형 메모리/로컬 임시 캐시는 가능하나 git에 커밋된 거대한 인덱스, 데몬, 외부 서비스, 복잡한 영구 그래프 금지. 변경 시 정확 무효화하고 의심될 경우 재탐색한다.
5. **짧은 출력·안전한 실패:** CLI는 `node scripts/codex-impact-map.mjs --changed` 및 `--file src/artifact/<파일>.js` 동작을 구현 목표로 삼는다. 간결한 사람용 요약과 필요시 `--json` 출력; 현재 HEAD/변경 상태, 확인된 근거, 테스트 후보와 미확인 영향 범위를 표시한다. 전체 소스·전체 테스트 로그를 기본으로 출력하지 않는다. 오류 시 유용한 원인과 Git/rg 수동 대체법을 남긴다.
6. **실제 수용 검사:** 최소 ① `series.js`→스크림/기록 ② `contracts.js`→FA/등록 ③ `season.js`→세이브/대회 ④ UI 단일 파일 ⑤ 무관/간접 함수 ⑥ staged/unstaged/untracked·rename/delete·브랜치 전환 사례. **잘못된 연결을 확정으로 속이지 않고, 정확한 HEAD/dirty 변화에 따라 오래된 결과가 갱신됨**을 검증한다. 구현 전후 실행 시간/출력 분량을 기존 `rg` 접근과 비교하여 실제 이득을 기록한다.

**완료 기준:** CLI와 실제 검사/근거를 포함한 소형 PR, 집중+인접 수용, 빌드·기존 필수 check·**정확 최종 HEAD CI** 통과 및 #241 승인 절차 준수. 최소 기능이 검증되어야 0-B 완료이며, 문서만 추가하거나 후보를 보여준 사실을 게임 기능·수용 테스트 PASS라고 표시하지 않는다. 결과가 도움이 되지 않으면 원인/비교 데이터를 남기고 단순 Git/rg 절차로 돌아간다.

### 향후 선택 개선 (이번 0-B에서는 제외)

- **입력:** 현재 git 기준 SHA/PR base, 워킹트리 변경·신규 파일, 선택적 파일/함수, `scripts/artifact-modules.mjs`와 `package.json`·실제 러너 파일. `--changed` 및 `--file <path>` 같은 CLI 옵션은 **구현 목표**, 현재 존재하는 명령은 아니다.
- **출력:** 변경 파일 목록, engine/UI/scripts/기타 모듈 구분, 확인된 정의·직접 호출/소비자, 전역 상태·저장/역사 경계, 관련 테스트 **후보 + 파일/함수 근거**, 불확실한 간접 호출/동적 참조, 기준 HEAD/dirty 표시. 요약은 짧게, 자세한 JSON은 요청 시에만.
- **정확성:** LOL-GM은 여러 `src/artifact/*.js`를 `ARTIFACT_MODULES` 순서로 조립하므로 **ES import 그래프만으로 의존성을 판정하면 안 된다**. 파일/함수 식별자·실제 읽기/쓰기 및 `runEngineFixture`·테스트 러너와 함께 확인. 추정/확실한 연결/미확인을 구분하고 간접 호출은 누락 가능성을 알린다. 억지로 모든 전역 키·규칙을 완벽한 그래프라고 주장하지 않는다.
- **심화 증분 캐시(옵션):** MVP의 입력 동일성 확인을 넘어선 파일 단위 세분화/영구 인덱싱은 실제 계측으로 유용함이 확인될 때만 논의한다. 변경/브랜치 전환/manifest·runner 변경은 늘 보수적으로 무효화하고 생성 출력은 게임의 역사/빌드/세이브에 넣지 않는다.
- **경계:** 게임 엔진 함수 변경, 별도 경기 엔진, CI 범위·테스트 필수 요건 축소, 새로운 외부 API·의존성 도입 금지. 파일 변경량이 큰 경우에도 호출하지 않은 전체 파일을 잔뜩 출력하지 않는다.
- **검증:** (a) 경기 `series.js`→스크림/경기 기록, (b) `contracts.js`→FA/계약·등록, (c) `season.js`→리그/세이브, (d) UI 파일만 변경, (e) 불분명한 동적 참조/무관 파일, (f) 신규·삭제·rename/미커밋 파일 및 branch 전환의 실제 코드+fixture 사례. 각 사례에서 **근거 있는 관련 테스트 후보**를 반환하고 없는 관계를 꾸며내지 않음을 검증한다.
- **성능/실익:** 첫 전체 스캔·증분 조회에 걸린 시간과 파일 수·토큰에 전달한 출력 줄 수를 기록해 기존 `rg` 절차와 비교. 이득이 입증되지 않으면 복잡한 상시 색인 엔진을 도입하지 않는다.

## 3. Codex 운영 지침에 붙이는 짧은 규칙

- **시작:** 마지막 체크포인트 → 변경 파일 식별 → 해당 파일의 직접 소비자 및 인접 테스트 확인 → 수정/검증. 매회 저장소 전체 지도 작성·문서 전수 재읽기 금지.
- **완료:** 관련 집중·인접·빌드 확인 뒤 **기존 필수 전체 check·정확 최종 HEAD CI / #241 검증**. 코드 맵의 '테스트 후보'는 반드시 실제 실행·증거를 통해서만 PASS가 된다.
- **인수인계:** 0-A 문서 반영 여부 → 0-B CLI 구현/검증 여부를 각각 기록한다. 0-B 완료 다음 실행부터 현재 이슈/PR·HEAD, 실제 변경 파일, 관련 소비자/테스트 1~3개, 마지막 검사/다음 명령만 기재. **검증되지 않은 CLI는 사용하지 않고 위 Git/rg 절차로 대체**한다. 코드 맵 생성 자체는 게임 기능 완료 증거가 아니다.
