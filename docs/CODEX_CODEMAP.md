# Codex 변경 파일 중심 코드 맵 — 재개 시 최소 탐색 규칙

> **상태:** 사용 가능한 Git 검색 절차 + 향후 Codex 자체 생성 도구의 구현 계약. 지금 저장소에는 `scripts/codex-impact-map.mjs`가 **아직 없으므로 존재하는 명령처럼 실행하지 않는다**. 단독 개발자는 기존 Codex이며 별도 담당/에이전트나 신규 정기 예약을 두지 않는다. 코드 맵은 **탐색 힌트**이지 실제 의존성/테스트 통과를 증명하지 않는다.

## 1. 지금 즉시 사용: 변경 범위만 좁혀 보기

1. **현재 이슈·PR 체크포인트·정확 HEAD부터 확인.** 우선 `git status --short`, `git log -1 --oneline`과 담당 PR 파일 목록을 확인한다. 완료된 이슈를 다시 분석하지 않는다.
2. **변경된 추적 파일·신규 파일을 모두 파악.** 로컬에서 origin/main을 조회할 수 있는 경우 아래 예시를 사용한다. 다른 기준 브랜치나 PR base라면 실제 base를 쓴다.

```sh
git diff --name-only "$(git merge-base origin/main HEAD)" HEAD
git diff --name-only
git ls-files --others --exclude-standard
```

3. **모듈 구분은 기존 manifest의 실제 목록으로.** `scripts/artifact-modules.mjs`의 `ENGINE_MODULES`/`UI_MODULES`을 조회하고 `src/artifact/`의 조립 순서를 확인한다. 모듈 개수를 하드코딩하지 않는다.
4. **해당 함수·상태 키 중심 소비자·연관 테스트 후보를 검색.** 먼저 변경된 파일의 함수 정의, 호출/전역 상태 읽기·쓰기와 키워드를 찾고, 확인된 식별자만 관련 소스·테스트에서 검색한다.

```sh
rg -n '변경한함수명|실제상태키' src/artifact scripts --glob '*.js' --glob '*.mjs'
rg -l '변경한함수명|실제상태키' scripts --glob '*acceptance*.mjs' --glob '*runner*.mjs'
```

5. 후보 테스트는 `package.json`의 실제 명령, `scripts/*runner*.mjs`의 임포트, `scripts/test-harness.mjs`의 실제 fixture 로딩을 확인한다. 단순 파일명 일치만으로 커버리지를 주장하지 않는다. 확인된 테스트가 없다면 **미확인**으로 표시한다.
6. **바뀐 원본 writer → 소비 함수 → UI/세이브·당시 역사 → 집중·인접 테스트**만 읽고 작업한다. 공통 세계 시계/경기 결과/계약·재정/시드와 연동되면 인접 모듈을 반드시 추가 조회한다. 변경 파일 외 영향 없음이라고 단정하지 않는다.

## 2. 자동 코드 맵 도구 — Codex가 실제 구현할 때의 계약

실제 개발 이슈를 수행하는 **동일 Codex가**, 영향 범위 탐색이 반복되어 실익이 있을 때 기존 개발 큐를 방해하지 않는 **소형 독립 PR**로 구현한다. 별도 AI·다른 모델·역할 분담 금지. 기능이 아직 없으면 위 기존 Git/rg 조회로 정상 개발을 진행한다.

- **입력:** 현재 git 기준 SHA/PR base, 워킹트리 변경·신규 파일, 선택적 파일/함수, `scripts/artifact-modules.mjs`와 `package.json`·실제 러너 파일. `--changed` 및 `--file <path>` 같은 CLI 옵션은 **구현 목표**, 현재 존재하는 명령은 아니다.
- **출력:** 변경 파일 목록, engine/UI/scripts/기타 모듈 구분, 확인된 정의·직접 호출/소비자, 전역 상태·저장/역사 경계, 관련 테스트 **후보 + 파일/함수 근거**, 불확실한 간접 호출/동적 참조, 기준 HEAD/dirty 표시. 요약은 짧게, 자세한 JSON은 요청 시에만.
- **정확성:** LOL-GM은 여러 `src/artifact/*.js`를 `ARTIFACT_MODULES` 순서로 조립하므로 **ES import 그래프만으로 의존성을 판정하면 안 된다**. 파일/함수 식별자·실제 읽기/쓰기 및 `runEngineFixture`·테스트 러너와 함께 확인. 추정/확실한 연결/미확인을 구분하고 간접 호출은 누락 가능성을 알린다. 억지로 모든 전역 키·규칙을 완벽한 그래프라고 주장하지 않는다.
- **증분·캐시:** 마지막 유효 HEAD/스캔 기준과 변경 파일을 구분. 동일 기준·변경 없음은 불필요하게 재스캔하지 않고, 변경/브랜치 전환/manifest·runner 변경 시 관련 후보를 무효화한다. 생성 출력은 게임의 영구 역사/빌드 산출물이나 세이브에 넣지 않는다.
- **경계:** 게임 엔진 함수 변경, 별도 경기 엔진, CI 범위·테스트 필수 요건 축소, 새로운 외부 API·의존성 도입 금지. 파일 변경량이 큰 경우에도 호출하지 않은 전체 파일을 잔뜩 출력하지 않는다.
- **검증:** (a) 경기 `series.js`→스크림/경기 기록, (b) `contracts.js`→FA/계약·등록, (c) `season.js`→리그/세이브, (d) UI 파일만 변경, (e) 불분명한 동적 참조/무관 파일, (f) 신규·삭제·rename/미커밋 파일 및 branch 전환의 실제 코드+fixture 사례. 각 사례에서 **근거 있는 관련 테스트 후보**를 반환하고 없는 관계를 꾸며내지 않음을 검증한다.
- **성능/실익:** 첫 전체 스캔·증분 조회에 걸린 시간과 파일 수·토큰에 전달한 출력 줄 수를 기록해 기존 `rg` 절차와 비교. 이득이 입증되지 않으면 복잡한 상시 색인 엔진을 도입하지 않는다.

## 3. Codex 운영 지침에 붙이는 짧은 규칙

- **시작:** 마지막 체크포인트 → 변경 파일 식별 → 해당 파일의 직접 소비자 및 인접 테스트 확인 → 수정/검증. 매회 저장소 전체 지도 작성·문서 전수 재읽기 금지.
- **완료:** 관련 집중·인접·빌드 확인 뒤 **기존 필수 전체 check·정확 최종 HEAD CI / #241 검증**. 코드 맵의 '테스트 후보'는 반드시 실제 실행·증거를 통해서만 PASS가 된다.
- **인수인계:** 현재 이슈/PR·HEAD, 실제 변경 파일, 관련 소비자/테스트 1~3개, 마지막 검사/다음 명령만 기재. 코드 맵 생성 자체는 게임 기능 완료 증거가 아니다.
