# LOL-GM — Codex 단독 5시간 사용량 주기 예약 운영 계약

> 작성: 2026-10-17 · 지위: **Codex 예약 설정에 적용할 명세/복사 프롬프트**. GitHub 파일 생성만으로 사용자의 실제 Codex Automation 예약이 생성·수정되지는 않는다. **코덱스 단독 코드 구현** 원칙을 유지하며 ChatGPT Work/다른 모델·다른 에이전트를 대체 개발자로 사용하지 않는다.

## 1. 목적과 확인된 한도 동작

OpenAI 사용량 안내(2026-10-17 기준): 해당 요금제/좌석에서는 **5시간 사용량 창 + 별도의 주간 창**이 존재할 수 있다. 5시간 창은 이전 창이 끝난 **이후 첫 Work/Codex 요청**으로 다음 창이 시작된다. '매일 00/05/10/15/20시 고정 리셋'이 아니다. 사용량은 단순 실행시간이 아니라 모델·작업·설정/도구 등에 따라 소모된다. **창이 5시간마다 돌아온다고 주간 사용량이 다시 채워지지는 않는다.**

사용량 확인: Codex/데스크톱의 Settings → Usage에서 **현재 5h 한도, 정확한 다음 리셋 시각, 주간 잔여량/주간 리셋**을 확인한다. 매 예약에서 사용량 상태를 볼 수 없으면 '사용 가능'으로 단정하지 않고 현재 툴/계정 표시의 실제 오류를 바탕으로 진행/중단. 사용량 없는 상태로 문서 전체를 읽거나 무의미한 분석·빈 실행을 반복하지 않는다.

## 2. 권장 일정과 실행시간

| 변수 | 기본값 | 이유 / 실제 실행 동작 |
| --- | --- | --- |
| `CADENCE` | **5시간 10분 간격 (310분)** | 5h 제한보다 +10분 여유. 시작 시간에서 매 310분이므로 자정 이후에도 위상이 정확히 계속 이동. |
| `ANCHOR` | **실제 사용량 페이지의 다음 5h 리셋 직후 첫 실행** | 현재 시계의 정각이나 서버·사용자가 임의 추정한 한도 리셋 시각을 기준으로 강제 시작하지 않는다. |
| `SOFT_CAP` | **1회 약 90분** | 5h마다 돌아오는 할당량으로 복잡한 실제 코딩 + 인접 회귀/인계. 시간은 **목표 상한**일 뿐 Codex 런타임 강제 timeout 보장 아님. |
| `IMPLEMENT` | **약 70분** | 현재 가장 앞선 미완료 작업의 최소 수정·회귀, 중간 중단 가능. |
| `WRAP_UP` | **마지막 약 20분** | 집중/인접 검사, 빌드·필수 CI 상태 확인, PR/진행 메모·원본 실패 근거 보존. |
| `PARALLEL` | **1** | 이전 작업과 겹쳐 동일한 파일·브랜치·할당량을 중복 소비하는 예약 금지. |
| `REPORT_CADENCE` | **매 실행 GitHub 짧은 인계, 사용자 요약은 원하면 6시간마다 별도/매 실행 Triage** | 결과가 없을 때 새 Codex 모델 요청까지 유발하는 무의미한 보고 생략. 보고 목적만으로 별도의 Codex 예약을 늘리지 않는다. |

**주의:** Codex 예약 UI에서 정확한 310분 간격/분 단위 `FREQ=MINUTELY;INTERVAL=310`을 지원하는지 확인한 후 사용. Codex *standalone automation*의 일부 custom schedule은 cron만 받으며, 일반 cron의 `0 */5 * * *`는 자정 경계에 **4시간 간격 구간이 생겨 정확한 매 5시간이 아니다**. 분단위 간격을 지원하지 않으면 **차선으로 6시간마다 정각** (예: `0 */6 * * *`, 00/06/12/18 KST) 을 적용. 사용할 수 없는 문법을 넣고 예약이 성공한 것으로 보고하지 않는다.

**기존 1시간마다 한 번인 예약 하나를 수정/대체**하며, 이전 예약을 그대로 두고 새 예약을 중복 추가하지 않는다. 예약 변경 전·후 실제 트리거/다음 실행 시각을 확인한다. 예약 생성/수정 API 권한이 없으면 아래 입력을 사용자에게 제시하고 '직접 예약 변경은 미실행'이라고 명시.

## 3. 매 예약 실행용 코덱스 프롬프트 (그대로 복사)

당신은 `lkh0802a/LOL-GM`의 **유일한 게임 코드 개발 담당 Codex**입니다. 이 명령은 **5시간 사용량 리셋을 효율적으로 활용하는 반복 개발 예약**입니다.

운영 변수: `CADENCE=5h10m`, `SOFT_CAP=90m`, `IMPLEMENT=70m`, `WRAP_UP=20m`, `PARALLEL=1`. 예약 기능에서 달리 설정됐다면 실제 예약 UI/툴에서 확인한 값을 우선합니다. 시간을 전부 채우는 것보다 완료된 검증 가능 변경이 우선입니다.

1. 현재 사용량/리셋 시각·주간 잔여량과 **선행 예약 실행/열린 PR**을 확인합니다. 이전 실행이 아직 진행 중이라면 새 게임 코드 변경을 시작하지 않습니다. 5시간 사용량이 부족하거나 주간 한도를 소진했다면 반복 호출/모델 전환·결제 없이 상태와 다음 재개 조건만 간단히 남기고 종료합니다. 볼 수 없는 잔여량을 임의 수치로 주장하지 않습니다.
2. [AGENTS.md](../AGENTS.md) → 현재 대상 이슈 본문/관련 최근 댓글 → 최신 main·작업 브랜치/해당 코드·테스트부터 읽습니다. **마스터·33개 분야·46만 자 개발 계획 전체를 매번 읽지 않습니다.** 규칙/연결이 불명확하면 관련 조항만 검색합니다.
3. [#242 우선순위](https://github.com/lkh0802a/LOL-GM/issues/242)에 따라 제일 높은 **미완료 실제 구현 이슈 하나**를 계속합니다: **#243 → #244 → P1(#245,#246,#248,#249,#247,#234,#224,#225) → P2(#250,#233,#232,#235,#236,#237,#238,#239,#240)**. #242는 추적, #241은 모든 PR의 상시 수용 기준입니다.
4. 실제 코드 원인/최소 재현을 검사하고 **한 이슈의 하나 이상의 연속된 검증 가능한 소형 작업**을 수행합니다. 가능한 시간·사용량이 남고 앞선 변경이 안전하게 검증되면 같은 이슈의 다음 독립 소형 수용 단위까지 이어갑니다. 중복 재조사/새 이슈·장문 계획만 작성하며 실행을 마치지 않습니다. 새 대형 엔진 전체 재작성/병렬 다른 모델 사용 금지.
5. 코드 수정은 `src/artifact/`의 원래 writer/consumer 경계를 우선 활용. 화면·훈련/게임 결과 단일원본, 세계시간/합의와 최종 서명, AI 합법 정보·예산/권한·계약, 당시 패치/역사, 원자적 세이브 불변식 유지. **기존 성공 기능 삭제/데이터 숫자 창작/테스트 완화 금지.**
6. **종료 전 약 20분을 검증/인계에 확보할 것을 목표**로 합니다. 집중 + 인접 회귀·`npm run build`; 실제 PR 완료에 필요한 필수 `npm run check`/정확 final-head CI(비용/시간이 허락하지 않으면 미실행이라고 보고) 확인. 작업 종료 시간이 임박했다면 새 대형 변경을 열지 말고 변경 내용/테스트 상태·재개 지점을 안전하게 보존.
7. GitHub 해당 이슈/PR에 짧게 **변경 코드/원인/시드·테스트 PASS·FAIL·SKIPPED/커밋·브랜치/미완/다음 작은 작업**을 남깁니다. PR 생성/갱신 권한이 있으면 이어가며 완료 증거 없이는 Close/자동 main 병합/출시 완료 주장 금지.
8. 한도/실제 코딩 환경의 자동화 도구 권한이 허용되는 경우에만 기존 **단일 예약**의 일정/프롬프트/작업 상한을 수정할 수 있습니다. 변경 전 현재 설정을 읽고, 다음 실행 시작/주간 한도·작업 겹침/다른 예약·사용자 의도에 맞는지 검증하고, 변경 사항을 GitHub에 기록합니다. **예약 변경 기능이 노출되지 않으면 절대 수정됐다고 주장하지 말고 필요한 사용자 조작을 요청**합니다.
9. 반복 예약은 사용자의 한도를 우회하는 수단이 아니라 **사용 가능한 5h 창마다 안정적으로 작업을 재개**하는 방법입니다. 5h/주간 한도·Codex 시스템의 실행 시간 제한을 그대로 준수하고 차단된 작업은 다음 정상 창까지 멈춥니다.

## 4. 스케줄 변경과 조정 기준

초기 **실제 실행 2~3회** 후 Codex 설정 → Usage와 실행 기록에서 판단한다.

- 5시간 한도 사용 전 종료하고 코딩 할 일이 남았다면 `SOFT_CAP`을 110분 이내에서 점진적으로 늘릴 수 있다. 단, 예약 환경의 허용 시간이 확인된 경우만.
- 90분 내 할당량 소진·반복 중지·허술한 테스트/인계라면 `SOFT_CAP=60~75m`로 줄이고 집중 작업을 더 작게 나눌 것.
- 주간 한도가 반복적으로 먼저 바닥나면 5h 반복으로 사용량을 추가 생성할 수 없으므로 **6h 또는 8h 주기/우선순위가 높은 버그 위주**로 완화. 사용량 확인 목적의 별도 유료 호출은 만들지 않음.
- 한 번의 코드 수정으로 이슈 범위가 다 끝났다면 90분을 채우려고 불필요한 코드 수정·추가 문서/이슈 작업을 하지 말고 안전한 검증/인계 후 종료한다.
- 실제 Codex 예약 간격의 수정은 앱 UI/지원 툴에서 수행해야 한다. **GitHub에 CADENCE 값을 바꾸는 것만으로 실제 예약 시간이 변경되지는 않는다.**

## 6. 자주 발생할 수 있는 오류

- 사용량은 **'작업시간 90분' = '5시간 할당량 90분어치'**로 계산되지 않는다. 정확한 소모는 모델/입력 문맥/연산/도구에 따라 달라짐.
- 같은 5시간 창에서 예약을 1시간마다 5회 돌려도 사용량 한도는 5회로 증식하지 않는다.
- cron `0 */5 * * *`는 정확히 매 5시간이 아니다. 별도 스케줄러가 calendar hours로 리셋할 가능성을 사용량 안내 없이 가정하지 않는다.
- Codex의 **실제 작업 제한**이 90분보다 짧다면 예약 프롬프트로 강제 연장할 수 없으며 더 짧은 인수 단위로 바꿔야 한다.
- 기존 GitHub 문서가 길더라도 새로운 예약마다 한꺼번에 읽지 않으며, 그 문서들의 사용자 승인·품질 범위를 삭제하지 않는다.
