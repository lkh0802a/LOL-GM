# LOL-GM — Codex 단독 5시간 간격 연속 자동 개발 운영 계약

> 개정: 2026-10-18 · 적용 대상: **기존 Codex 개발 예약 한 개**. GitHub 문서·ChatGPT 일반 예약은 Codex Automation 설정 자체가 아니다. Codex 예약 편집 권한이 없다면 변경했다고 주장하지 않는다. 게임 코드 개발자는 기존 **Codex 모델 그대로** 유지한다.

## 1. 예약 및 실행 제한

- 기존 LOL-GM Codex 예약을 **수정**하고 중복 예약은 만들지 않는다. 현재 예약·모델·트리거·다음 실행·실행 중 작업을 먼저 확인한다.
- 예약 시스템이 정확한 경과시간 반복을 지원하면 **5시간(300분)마다 1회** 실행한다. 가능하면 다음 실제 사용량 갱신 이후 첫 실행으로 시작점을 잡는다. 5시간 사용량 창이 고정 정각에 리셋된다고 가정하지 않는다.
- 기존 **55분·120분 제한**, **90분 목표 상한**, **70분 구현+20분 정리 시간 배분**, 그 밖의 임의의 작업시간 상한을 제거한다. 검증 및 인수인계는 시간 할당으로 축소하지 않고 작업 완료 조건에 포함한다.
- 플랫폼이 실제로 허용하는 실행시간·모델 사용량·5시간/주간 한도 안에서 코드 개발을 최대한 진행한다. 프롬프트는 플랫폼의 강제 timeout 또는 사용량 제한을 변경할 수 없다.
- 기존 Codex 모델을 유지하고 모델 변경·별도 AI/Work 분담·유료 우회 사용을 전제로 하지 않는다.
- **동시 실행은 최대 1개**. 이전 실행이 아직 진행 중이거나 같은 브랜치/파일을 수정 중이라면 새 개발을 시작하지 않는다.
- 스케줄러가 경과시간 간격을 지원하지 않는다면 **'0 */5 * * *'를 정확한 5시간 반복으로 사용하지 않는다**(자정 경계에서 4시간 간격). 지원 가능한 실제 설정과 차선책을 보고하며, 다른 간격을 임의로 설정했다고 주장하지 않는다.
- 기존 Codex 예약을 읽거나 수정할 권한이 없으면 예약은 그대로 두고 필요한 변경값과 권한 문제를 보고한다. GitHub 문서 수정이 실제 예약 수정의 증거가 아니다.

## 2. 우선순위와 연속 진행

1. 저장소: **lkh0802a/LOL-GM**. 루트 AGENTS.md 및 GitHub **#242**의 최신 실행 순서가 우선한다.
2. **#255 CI 복구는 과거 완료**로 취급하고, #242의 **현재 순서 + 실제 이슈/PR 상태**에서 가장 앞선 미완료 작업을 재개한다. 이미 closed/merged·검증된 작업은 다시 착수하지 않는다. #242는 추적용이며 **#241은 모든 PR의 상시 검증 게이트**다.
3. 시작 조회는 **최근 재개 체크포인트 1개 → 최신 issue/PR·브랜치·HEAD·main 상태 → 마지막 바뀐 소스/인접 테스트** 순서로 최소화한다. 체크포인트가 부정확하거나 SHA가 바뀌었을 때만 관련 상세 이력/명세를 추가 조회한다. 기존 실행/CI가 살아 있다면 PID/run·동일 SHA를 확인하고 중복 명령을 실행하지 않는다.
4. 현재 이슈를 재현→최소 구현→집중/인접 회귀→빌드/필수 CI→근거 기록까지 실제 완료했다면, **같은 실행에서 다음 우선순위 이슈**로 계속 이동한다. 한 번의 실행에서 이슈 하나만 다루라는 제한은 없다.
5. 검증되지 않은 수정을 여러 이슈에 걸쳐 쌓지 않고, 충돌 PR·중복 writer·충돌 브랜치를 만들지 않는다. 안전하지 않은 경우 먼저 기존 변경을 보존·검증하고 진행한다.

## 3. 사용량을 실제 구현에 집중

- 매 실행마다 저장소·마스터 명세·33개 분야 문서·전체 DEVELOPMENT.md를 처음부터 재독하지 않는다.
- **AGENTS.md의 짧은 재개 체크포인트 → 관련 이슈/PR의 최신 근거 → 바뀐 코드/집중 테스트 → 필요한 상세 절** 순서로 읽는다. `#242`의 역사적 본문에 적힌 옛 '첫 작업 #243'보다 실제 최신 상태를 우선한다.
- 구체적 오류의 재현, 원인, 수정, 관련 테스트, 저장·시드·권한·UI 회귀 및 CI에 사용량을 우선 사용한다.
- 단순 분석 보고서, 반복 코드 탐색, 과도한 로그 출력·불필요한 재시도, 문서만 추가하는 작업으로 실행을 소진하지 않는다. 기존 `scripts/ci-run.mjs`가 만든 **JSON 결과·수행 시간·실패 꼬리 부분을 먼저 검사**하고, 상세 원본 로그는 실패 항목을 좁힌 뒤 필요한 위치만 조회한다. 증거 원문/종료코드는 지우거나 가리지 않는다.
- 사용량 한계가 도달하거나 플랫폼이 실행을 멈추면 작업을 안전하게 보존하고 중단한다. **한도 소진은 개발 완료가 아니다.**

## 4. 안전 불변식과 검증

- **코드 맵/변경 파일 탐색:** [CODEX_CODEMAP.md](CODEX_CODEMAP.md)의 즉시 사용 가능한 Git/rg 절차로 최신 변경 소스 → 실제 함수 소비자·관련 테스트 후보부터 조회한다. `scripts/artifact-modules.mjs`은 단순 import 그래프가 아니라 글로벌 조립 목록이다. 자동 코드 맵의 실제 제공/검증 상태는 CODEX_CODEMAP.md와 담당 PR의 정확 HEAD CI에서 확인한다. **사용자 최신 승인:** [#242 0-A](https://github.com/lkh0802a/LOL-GM/issues/242)에서 PR #264 문서를 검토/병합하고, **0-B에서 기존 단일 Codex가 최소 자동 코드 맵 CLI를 소형 PR로 한 번 구현·수용**한 뒤 즉시 #262 및 기존 P1/P2 작업으로 복귀한다. MVP는 변경 감지/직접 소비자·테스트 후보/동일 입력 재사용까지만, 완벽한 의존성 그래프·복잡한 상시 인덱스는 제외. 실제 필수 테스트/CI를 축소하지 않으며 미구현 도구를 실행했다고 말하지 않는다.

- src/artifact/의 실제 writer/consumer와 scripts/artifact-modules.mjs 조립 계약을 유지한다. 생성된 index.html·dist/index.html 직접 수정 금지.
- 스크림/공식 경기의 실제 실행 결과와 화면·기록·훈련 효과는 단일 원본이어야 한다. 세계 시계, 계약 합의와 감독 서명 구분, AI 합법 정보, 선수/의료/재정, 당시 경기 역사, 결정론, 세이브 원본을 보호한다.
- **수정 중에만** 관련 scripts/*-acceptance.mjs 집중 시험 → 영향받은 인접 회귀 → npm run build를 순서대로 확인한다. 여러 편집 단계마다 전체 검사를 새로 시작하지 않는다. **완료/PR에는** 원래 요구되는 npm run check·정확 최종 HEAD 필수 CI·#241 통합 검증 및 의료 샤드/집계 등 필수 게이트를 그대로 적용한다. CI의 기존 파일 범위 정책이나 필수 테스트 삭제/생략은 이 최적화의 대상이 아니다.
- 테스트 삭제·기대치 약화·실패 숨기기 금지. 필수 검증이 미실행/실패라면 이슈 완료·PR 완료/출시 완료를 주장하지 않는다.
- 한 이슈의 코드 구현과 검증이 모두 끝났을 때만 객관적 근거를 기록하고 다음 순위로 이동한다.

## 5. 종료·인수인계·재개

플랫폼 실행시간 종료, 한도, 장애, 중복 실행 위험 또는 작업 검증 경계에서는 **해당 GitHub 이슈/PR의 최신 댓글에 짧은 체크포인트를 1개** 남긴다. 이미 있는 세부 증거를 반복 게시하지 않는다.

```text
ISSUE/PR: #번호 / PR URL / branch / 정확 HEAD SHA
STATE: 재현 | 수정 중 | 검증 중 | 차단 | 완료(근거 필수)
DONE: 원인(file:line)·변경 파일·실제 수정 성과
TEST: 집중 / 인접 / build / check / 최종 HEAD CI = PASS·FAIL·미실행
BLOCK: 미확정·실패·현재 살아 있는 PID/CI run / 원본 증거 링크
NEXT: 다음 실행에서 바로 확인/실행할 파일·명령 1개
```

다음 예약은 최신 상태/진행 중 검사 결과부터 확인한 후 이어서 개발한다. **다른 SHA의 PASS 재사용, 미완성 검증 생략, 원본 실패·증거 삭제 금지**. 실제 완료되지 않은 중간 상태를 매 실행의 새 기획 문서로 확장하지 않는다.

## 6. 기존 Codex 예약의 **고정 부트스트랩 프롬프트** — 최신 지시는 실행 시 자동 조회

**예약 프롬프트를 GitHub 작업 번호에 맞춰 반복 수정하지 않는다.** 기존 예약 **한 개의 프롬프트를 아래 고정 부트스트랩으로 한 번만 교체**하면, 이후 매 실행 `main`과 최신 GitHub #242, 현재 이슈·PR·CI/인수인계를 조회하므로 **예약 프롬프트 변경 없이 실제 개발 우선순위가 자동 최신화**된다. 단, 이는 **Codex 예약 객체의 프롬프트/실행 시각을 물리적으로 다시 작성하는 기능이 아니다.** 기존 예약 수정 권한이 없으면 설정이 바뀌었다고 주장하지 않는다.

~~~text
당신은 lkh0802a/LOL-GM의 기존 단독 Codex 개발자입니다. 이 실행은 현재 예약의 1회 작업이며, 새 예약·다른 AI/작업자·동시 중복 실행을 만들지 마십시오. 기존 모델과 예약 간격은 유지하고 플랫폼 실제 사용량·시간 한도를 넘기려 하지 마십시오.

매 실행 시작 시 항상 최신 GitHub 상태에서 작업 지시를 새로 계산하십시오. 과거 예약 프롬프트의 이슈 번호·완료 당시 HEAD·날짜를 영구 시작 명령으로 취급하지 마십시오.

1. 저장소 최신 main과 현재 작업 브랜치/dirty 상태를 확인하십시오. AGENTS.md 및 docs/CODEX_AUTOMATION_5H.md의 운영 원칙을 필요한 부분만 읽으십시오.

4. 코드 맵 도구가 실제 존재하고 검증되어 있으면 변경 파일·관련 소비자·테스트 후보를 탐색할 때 사용하고, 없으면 Git diff/rg를 사용하십시오. 변경 파일/영향 범위만 먼저 읽되 세계 시계·세이브·정보권한 등 연결된 경계까지 검증하십시오.
5. 수정 중에는 집중 테스트·인접 회귀·빌드로 빠르게 확인하고, PR 완료 판정에는 기존 필수 전체 check·정확 최종 HEAD CI와 #241 기준을 모두 유지하십시오. 실패를 숨기거나 테스트 범위를 약화하지 마십시오. 긴 로그는 기존 결과 JSON/실패 부분부터 읽고 원문은 보존하십시오.
6. 중단 시 최신 이슈/PR에 ISSUE/PR·STATE·DONE·TEST(PASS/FAIL/미실행)·BLOCK·NEXT 체크포인트를 짧게 남기십시오. 실제 완료한 작업이 있으면 같은 실행에서 다음 미완료 작업으로 이동하십시오.

작업 우선순위가 바뀌어도 예약 프롬프트를 다시 쓰거나 새 예약을 만들지 마십시오. GitHub #242와 현재 main의 지침을 다음 실행 때 다시 로드하는 것이 자동 최신화 방식입니다. GitHub 접근이 차단되면 오래된 작업 번호로 추측해 실행하지 말고 안전하게 이전 체크포인트와 확인 가능한 정보만 사용하고 확인되지 않은 사항을 보고하십시오.
~~~

### 변경 사항의 자동 반영 방식

- **우선순위 수정:** 기존 [#242 실행 대기열](https://github.com/lkh0802a/LOL-GM/issues/242)의 **현행 최상단**과 관련 이슈/PR의 최신 상태를 수정한다. 다음 예약 실행에서 자동 재조회한다. #242의 과거 하단 표보다 최신 상태가 우선한다.
- **공통 운영 원칙 수정:** `AGENTS.md` / 이 문서의 **main 병합 내용**이 다음 실행부터 적용된다. 아직 Draft/open PR만 있는 변경은 완료된 정책/구현이라고 간주하지 않고, 해당 PR의 실제 내용과 검증 상태를 먼저 확인한다.
- **실제 실행/완료 기록:** 진행 중인 이슈/PR 최신 체크포인트와 최종 HEAD CI가 현재의 소유 상태다. 이슈 제목에 붙은 과거 `P1-xx` 번호만으로 작업 시작 여부를 판단하지 않는다.
- **오류나 충돌:** 현재 상태 조회가 불가능하면 안전한 기존 작업만 수행하고 **미확인**을 기록한다. 예전 예약 프롬프트를 임의 진실의 원천으로 되살리지 않는다.
- **실제 예약 설정:** 간격·모델·사용자 알림·대상 환경 등 **스케줄러 메타데이터는 자동 변경하지 않는다.** 변경이 필요하다면 기존 예약 한 개를 해당 예약 관리 기능에서 별도로 수정·확인한다. 예약 도구가 노출돼도 기본은 GitHub 최신 지시 로딩이며, 자동으로 예약 복제·삭제·재생성하지 않는다.

## 7. 적용 여부 구분

**GitHub에 이 문서와 AGENTS.md를 수정한 것**은 Codex 개발 지침의 변경이다. **실제 Codex Automation 트리거/실행 모델/실행시간 설정 변경**은 별도로 Codex 자체 예약 관리 기능에서 수행하고, 수정 전후의 트리거와 다음 실행 시각을 확인해야 한다. **ChatGPT의 별도 반복 작업 생성은 기존 Codex 예약을 수정하거나 Codex 모델로 코드를 실행하는 것과 동등하지 않다.**


## 8. 디스크 부족 재발 방지 — 원본 보존

- 착수와 긴 검사 전 `npm run check:space`를 실행한다. 기본 대상은 현재 작업 폴더가 아니라 스크립트가 속한 저장소 파일시스템이다. 가용 1GiB 미만은 BLOCKED(exit2), 용량 확인 실패는 UNKNOWN(exit3), 1~4GiB는 WARN이다. 임계값은 작업 여유 기준이며 플랫폼 디스크·메모리·계정 한도를 변경하지 않는다. `npm run check`는 이 점검 뒤 기존 검사를 전부 실행한다. 부족하면 먼저 원인을 조사하고, 원본 보존 조건을 만족할 수 없으면 차단을 기록한다.
- 새 검사 원문은 처음부터 무손실 gzip으로 기록하고 명령/정확 HEAD·소스 해시/시작·종료/종료코드/원문 길이·SHA256/압축 해제 동일성을 보관한다. 기존 실패 원문을 지우거나 요약만 남기지 않는다. 압축된 원문도 실제 원문 보존이며 검사는 축소하지 않는다.
- 기존 worktree를 우선 재사용한다. 다른 작업 폴더의 dirty/미추적/ignored/실행 프로세스가 불명확하면 정리하지 않는다. 소스·커밋·세이브·테스트 증거와 `docs/evidence/`는 캐시가 아니다. 자동 삭제·Git prune/gc·강제 worktree 제거를 하지 않는다. 실제 build writer가 확인된 임시 생성물만 비활성 상태에서 정리하며 필요하면 먼저 압축·해시 검증과 복원 receipt를 남긴다.
- `df -h`로 파일시스템을 구분한다. 별도 `/tmp`를 비우는 것이 저장소 디스크 확보라고 주장하지 않는다. 임시 파일시스템은 영속 증거의 대체 저장소가 아니다.
- `docs/evidence/`의 장기 저장 방식 변경은 파일별 실제 소비자/보존 필요/원문 SHA/복원 경로/기존 검사 수용을 검증하는 별도 변경으로만 제안한다. 원본 삭제나 외부 업로드를 전제로 자동 전환하지 않는다. 현재 증설·이전 도구가 없다는 사실과 제공자 측 기능 미확인을 구분한다.
